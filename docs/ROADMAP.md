# ギター練習帖 ロードマップ

この文書は、機能追加のたびに優先順位がぶれないようにするための実装方針です。
長期の能力モデルと測定設計は `ARCHITECTURE.md`、個別タスクの受け入れ条件は `TASK-*.md` を正とします。

## 1. 現在地

このアプリは、静的HTML / GitHub Pages / オフライン優先を維持しながら、次の基盤まで到達しています。

- 基礎・フレーズ・リズムの3モード統合
- 教材JSONと表示ロジックの分離
- AudioContext時刻を基準にした先読み再生
- VexFlow / Bravura による五線譜 + TAB
- 付点・連符・タイ・スラー・ベンド・スライド・H/P等の記譜モデル
- ナイロンギター、ベース、ドラムのサンプル再生
- Service Workerによるオフライン動作
- 単体テスト、データ検証、Playwright E2E
- 小節単位の反復、補助表示の段階的除去、練習条件付きAttempt記録（PR #11）

一方、まだ「演奏を測定し、弱点に応じて次の練習を処方する」閉ループには到達していません。

## 2. 実装順序

### P0 — 再生・計測の時間基盤を一つにする

`guitar.js` と `phrase.js` に残る先読みスケジューラを `core/clock.js` へ共通化します。
発音時刻は今後の録音・タイミング測定・カウントイン・区間再生の基準になるため、機能追加より先に単一の時計へ寄せます。

- AudioContext.currentTime を唯一の発音基準にする
- `setInterval` / `setTimeout` は予約キュー補充・UI用途に限定する
- lookahead の既定値を 0.15 秒へ統一する
- 再生中のテンポ変更は次スロットから反映する
- `core/` はブラウザグローバルを直接参照しない

詳細: `TASK-NEXT-CLOCK.md`

### P1 — 録音と自己モニタリング

スマホのマイクから演奏を録音し、同じAttemptに紐付けて聴き返せるようにします。
最初から自動採点を行わず、録音 → 再生 → ルーブリック自己評価を先に成立させます。

狙い:

- `ear.selfmonitor` を実際の練習フローへ組み込む
- 不要弦、音量差、音色差、フレージングを本人が確認できる
- 後の自動測定用にAttemptと録音の関係を固定する

### P1 — Attempt / 測定基盤

自己申告と機械測定を混ぜません。

- Tier A: タイミング、単音ピッチ、RMS、完遂率など自動測定
- Tier B: 録音 + ルーブリック評価
- Tier C: 集中・不安・表現意図など自己申告

自動測定を入れる前に端末ごとの入出力レイテンシ校正を設計します。校正なしのタイミング値を成績として保存してはいけません。

### P1 — WebKit / Safari 最小回帰

Chromium E2Eに加え、WebKitで最低限のsmoke suiteを持ちます。

対象:

- 起動
- フレーズ読込
- 譜面描画
- 再生開始 / 停止
- IndexedDB保存
- Service Worker / オフライン復帰

全E2Eを二重化する必要はありません。Web Audio・IndexedDB・PWA境界だけを守ります。

### P2 — 教材を能力モデルへ接続する

エンジンに対して教材量が少ないため、コードを増やすだけでなく教材を能力IDに結び付けて拡張します。

優先教材:

- 弦移動
- ハイブリッドピッキング
- クロマチック / ポジション移動
- コードトーン
- 16分アクセント / 3連
- 低音 + 旋律
- 初見
- 暗譜と途中小節からの再開

教材固有の分岐をコードに書かず、JSON側で能力・難度・前提を表現できる形を優先します。

### P2 — 記譜モデルの拡張

特殊奏法の種類を増やすより先に、音楽構造として不足しているものを埋めます。

1. 休符
2. 複声部
3. フレーズ側の任意拍子

特にフィンガースタイルでは低音の持続と上声の旋律が独立するため、複声部は重要です。

### P2 — 音源ロード戦略

サンプル数が増えた段階で、Service Workerのキャッシュと AudioBuffer のdecodeを分離します。

- ファイルはオフライン用にキャッシュ可能
- decodeは必要な音域・奏法だけ遅延ロード
- 全奏法・全ベロシティを初回にdecodeしない

### P3 — 音源取込・パート分離・自動採譜

これは練習プレイヤー内部へ直接押し込まず、独立した Import / Analysis pipeline とします。

```text
音源ファイル
  ↓
stem separation
  ↓
ギターパート
  ↓
onset / pitch / polyphonic transcription
  ↓
中間ノートモデル
  ↓
人間による修正
  ↓
phrases.json / MusicXML
```

自動採譜結果を無検証で教材へ公開しません。既存の音名/TAB/記譜バリデータを最終ゲートとして再利用します。

## 3. 優先順位の判断基準

新機能案は次の順で評価します。

1. 練習のフィードバックループを閉じるか
2. 時間・記録・測定の信頼性を上げるか
3. 実際のギター技能の弱点を切り分けられるか
4. 教材追加時にコード分岐を増やさないか
5. オフライン・静的配信・モバイル利用を壊さないか

「見た目が豪華になる」「機能数が増える」だけでは優先しません。

## 4. 非目標

当面、次は行いません。

- フレームワーク / TypeScript / バンドラ導入
- サーバー必須化
- 校正なしの精密タイミング採点
- 自己申告と自動測定を同じスコアとして表示
- 自動採譜結果の無検証公開
- 教材固有ロジックのJavaScriptへの埋め込み
