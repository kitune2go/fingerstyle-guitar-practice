## 0. フェーズ運用ルール

今後は P0 / P1 / P2 のような重複優先度ではなく、**Phase 0〜7 の直列段階**で進捗を管理します。

### 必須ルール

1. `docs/ROADMAP.md` の先頭には常に **CURRENT PHASE** を1つだけ明記する
2. 各 `TASK-*.md` の冒頭に `CURRENT PHASE` と `NEXT PHASE` を明記する
3. 各PR本文に、対象PhaseとそのPhaseの完了条件を明記する
4. Phaseを完了させるPRは、完了条件を全て満たすまで次Phaseの機能を混ぜない
5. 次Phaseの最初のコミットで `CURRENT PHASE` を更新してから実装を始める
6. 完了報告では必ず次を明記する
   - 作業開始時のPhase
   - 作業終了時のPhase
   - Phase完了 / 継続のどちらか
   - 次のPhaseまたは次タスク

「何を実装したか」だけでなく、**ロードマップのどこまで到達したか**を必ず報告対象にします。

## 4. Phase 2 — 共通時間基盤

**状態: DONE — PR #12**

目的:

`guitar.js` と `phrase.js` に重複していた先読みスケジューラを `core/clock.js` へ集約し、再生・録音・将来の測定が同じ時間概念を使える状態にします。

不変条件:

- `AudioContext.currentTime` を発音時刻の基準とする
- `setInterval` / `setTimeout` から直接発音しない
- lookahead は 0.15 秒
- `core/clock.js` はブラウザグローバルを直接参照しない
- フレーズ固有の音符・小節・ループ・Attempt状態をclockへ持ち込まない

詳細: `TASK-NEXT-CLOCK.md`

Phase 2 完了後、この時計を再設計するのではなく、Phase 3以降が利用する基盤として固定します。

## 5. Phase 3 — 録音・自己モニタリング

**状態: CURRENT**

目的:

スマートフォンのマイクから演奏を録音し、同じ練習Attemptと対応付けて聴き返せるようにします。
最初から自動採点は行いません。

成立させる練習ループ:

```text
練習条件を決める
  ↓
録音しながら演奏
  ↓
停止
  ↓
録音を聴き返す
  ↓
簡単なルーブリックで自己評価
  ↓
Attemptとして保存
```

狙い:

- `ear.selfmonitor` を実際の練習フローへ入れる
- 不要弦、粒、音色、フレージングを本人が確認できる
- 後の自動測定へ進む前に Attempt と録音の関係を固定する
- マイク権限拒否や録音非対応でも通常練習を壊さない

詳細: `TASK-NEXT-RECORDING.md`

**このPhaseではタイミング自動採点・ピッチ採点を実装しません。**

## 6. Phase 4 — 測定・処方基盤

**状態: NEXT**

目的:

「録音した」から「弱点を測り、次の練習条件を処方する」へ進みます。

記録を混同しません。

- Tier A / `measured`: タイミング、単音ピッチ、RMS、完遂率等の自動測定
- Tier B / `observed`: 録音とルーブリック等、演奏を見聞きして得る評価
- Tier C / `reported`: 集中、不安、本人の感覚等の自己申告

必須事項:

- 入出力レイテンシ校正
- accuracy（偏り）と precision（ばらつき）の分離
- 測定不能な項目を偽の数値へ変換しない
- 能力IDへ測定結果を接続する
- 同じ条件のAttempt履歴から次のテンポ・補助・区間を提案する

**校正なしのタイミング値を成績として保存してはいけません。**

## 7. Phase 5 — Safari / WebKit 信頼性

**状態: PLANNED**

Chromiumだけではスマートフォン実運用の保証として不足するため、WebKitで最小smoke suiteを持ちます。

対象:

- 起動
- フレーズ読込
- 譜面描画
- AudioContext再生開始 / 停止
- マイク録音開始 / 停止
- IndexedDB保存
- Service Worker / オフライン復帰

全E2Eを二重化せず、Web Audio・MediaRecorder・IndexedDB・PWA境界を重点的に守ります。

## 8. Phase 6 — 教材・記譜・音源の拡張

**状態: PLANNED**

基盤と測定が成立した後、教材量と表現力を増やします。

### 教材

能力IDと結び付けて増やします。

- 弦移動
- ハイブリッドピッキング
- クロマチック / ポジション移動
- コードトーン
- 16分アクセント / 3連
- 低音 + 旋律
- 初見
- 暗譜と途中小節からの再開

教材固有の分岐をJavaScriptへ埋め込まず、JSON側で能力・難度・前提を表現します。

### 記譜

特殊奏法を増やす前に構造上の不足を埋めます。

1. 休符
2. 複声部
3. フレーズ側の任意拍子

特にフィンガースタイルでは低音と旋律が別の長さで進むため、複声部が重要です。

### 音源

サンプル数が増えた段階で、Service Workerのキャッシュと AudioBuffer decodeを分離します。

- ファイル自体はオフライン用にキャッシュ
- decodeは必要な音域・奏法だけ遅延実行
- 全奏法・全ベロシティを初回にdecodeしない

## 9. Phase 7 — 音源取込・パート分離・自動採譜

**状態: FUTURE**

練習プレイヤー内部へ直接押し込まず、独立した Import / Analysis pipeline とします。

```text
音源ファイル
  ↓
stem separation
  ↓
ギターパート
  ↓
onset / pitch / polyphonic transcription
  ↓
中間ノートモデル
  ↓
人間による修正
  ↓
phrases.json / MusicXML
```

自動採譜結果を無検証で教材へ公開しません。
既存の音名 / TAB / 記譜バリデータを最終ゲートとして再利用します。

## 10. 優先順位の判断基準

新機能案は次の順で評価します。

1. 現在Phaseの完了条件に必要か
2. 練習のフィードバックループを閉じるか
3. 時間・記録・測定の信頼性を上げるか
4. 実際のギター技能の弱点を切り分けられるか
5. 教材追加時にコード分岐を増やさないか
6. オフライン・静的配信・モバイル利用を壊さないか

「見た目が豪華になる」「機能数が増える」だけではPhaseを飛ばしません。

## 11. 非目標

当面、次は行いません。

- フレームワーク / TypeScript / バンドラ導入

- 校正なしの精密タイミング採点

- 自動採譜結果の無検証公開
- 教材固有ロジックのJavaScriptへの埋め込み
- Current Phaseを更新せずに次段階の機能を混ぜること
